# 漂语 · 决策插件开发计划（插件化版）

> 版本：V3.0（取代 V2.0）
> 定位：**漂语不是独立 App，而是 twin-platform 的一个领域插件（`plugins-fishing`）+ 一个领域无关的决策内核（`decision-core`）。**
> 核心原则不变：**本地确定性计算负责事实，规则负责明确判断，Jev 负责不确定决策，模板负责解释，用户反馈负责校准。**

## 1. 为什么是插件，不是新项目

上一轮已经定了：台钓是“工业决策系统”的最小实验场，不是跑题的小玩具。一旦另起仓库，`State → Judgment → Action → Outcome → Learning` 就会各自演化，工厂阶段无法复用。

在 twin-platform 里，这件事有现成的先例：**`analytics-core` 是领域无关的指标内核，插件用 `MetricDescriptor` 声明“我有什么指标”，宿主负责装配。** 决策应该完全照这个模式做：**`decision-core` 是领域无关的决策内核，插件用 `DecisionDomain` 声明“我的状态、动作空间、判断与评分”。**

```text
analytics-core  (纯函数指标内核)  <── MetricDescriptor ──  plugins-logistics / plugins-fishing
decision-core   (纯函数决策内核)  <── DecisionDomain   ──  plugins-logistics / plugins-fishing
```

两者都不认识“输送线”，也不认识“台钓”。

## 4. 决策契约（`decision-core`）

```ts
/** 领域状态：由 Environment 观测得到，必须可序列化。 */
export interface DecisionState { readonly kind: string }

/** 一次判断的完整结果。Jev 也只允许产出这个结构。 */
export interface Decision<A extends string = string> {
  /** 唯一动作 id（封闭枚举）。 */
  action: A;
  /** 动作参数；每个字段都必须在该动作的值域内。 */
  params: Readonly<Record<string, number | string>>;
  /** 0..1；必须参与校准。 */
  confidence: number;
  /** 机器可读的原因码，不承载文案。 */
  reasonCode: string;
  /** 决策时的状态摘要哈希，用于配对观测。 */
  stateHash: string;
  /** 预期会发生什么（用于事后评测，不是给用户看的）。 */
  predicted?: Readonly<Record<string, number | string>>;
}

/** 判断者：规则与 Jev 是同一端口的两个实现。 */
export interface Judge<S extends DecisionState> {
  readonly id: string;
  judge(state: S, context: JudgeContext): Promise<Decision> | Decision;
}

/** 策略：把 Judge 的输出夹取到合法动作空间（越界即拒绝或降级）。 */
export interface Policy<S extends DecisionState> {
  validate(state: S, decision: Decision): DecisionVerdict;
}

/** 环境：仿真或真实记录，都必须能给出下一段观测。 */
export interface Environment<S extends DecisionState> {
  observe(): S;
  /** 执行动作并推进到下一次可观测点。 */
  step(action: Decision['params']): Outcome;
}

/** 执行器：钓鱼是“发给用户”，工厂是“调 MCP”。 */
export interface Executor<A> {
  execute(decision: Decision<A>): Promise<void>;
}
```

**三条铁律**（写进 `decision-core` 的文档与测试）：

1. **同步 + 确定性**：`engine.decide(state)` 在给定 `Judge` 与 seed 下必须逐位可复现，测试用指纹比对，和 `world-kernel` 同一套方法论。
2. **Judge 输出必须过 Policy**：模型/solver 的自由输出一律视为“未经校验的提议”，越界即夹取或降级为 `OBSERVE`，绝不放行。
3. **`decision-core` 不依赖 MCP、不依赖 LLM SDK、不依赖 UI**：Jev 是外部实现，通过 `Judge` 端口注入。

## 6. Fishing Core（原 Phase 0/1 搬进 `plugins-fishing`）

### 6.1 调钓计算

```ts
H  = t0 - t
hw = H / 2

d1 = t - 2 * w
d2 = t - w + hw
d3 = t0

span = d3 - d1
B = d + 2 * w - t
```

约定（**必须在 `docs/台钓模型.md` 里写明，并由测试固化**）：

- `t0` 无钩调目、`t` 带钩调目、`d` 当前钓目，单位都是“漂尾目数”；
- **`w` 是“单饵压目数”，不是克。** 装备库里的“单饵重”字段名有歧义，实现时以“压目”为准；称重向导测的是“单饵压几目”。
- `H` 是双钩压目、`hw` 是单钩压目。

### 6.2 状态判断

| B | 状态 | 临界点 |
| --- | --- | --- |
| `B <= 0` | 未到底 | `d1 = t - 2w` |
| `0 < B < hw + w` | 灵区 | |
| `B = hw + w` | 不灵不钝 | `d2 = t - w + hw` |
| `hw + w < B < H + 2w` | 钝区 | |
| `B >= H + 2w` | 铅坠触底 | `d3 = t0` |

> 推导自洽性：`B = d + 2w - t`，代入三个临界钓目分别得 `B=0`、`B=hw+w`、`B=H+2w`，与状态表四段分区一一对应。
> “不灵不钝 = 下钩饵全着底、上钩饵全悬”是一个流派约定，不同流派边界不同——**必须显式声明，不能默认**。

### 6.3 显式假设（v1 的简化，越界即不确定）

双饵等重、双钩等重、忽略钩距在目数上的贡献、漂尾线性、不考虑子线弯曲支撑、不考虑饵料溶散。

### 6.4 动作空间（封闭枚举，可逆优先）

```ts
type FishingAction =
  | 'NO_CHANGE'            // 继续观察
  | 'ADJUST_FLOAT'         // 上推=钝 / 下推=灵，步长 0.5 | 1 | 2 目     可逆
  | 'CHANGE_BAIT'          // 味型 / 状态 / 大小                            可逆
  | 'CHANGE_LAYER'         // 上 / 下，幅度 0.5 | 1 个水深带                可逆
  | 'REFILL_NEST'          // 轻 / 常规 / 重                                 半可逆
  | 'REBUILD_RIG'          // 换钩 / 换线 / 换漂                            ★不可逆
  | 'CHANGE_SPOT'          // 换钓位                                        ★不可逆
  | 'OBSERVE';             // 明确要求再打 N 竿
```

**`Policy` 的责任**：把 V2.0 第 8.2 节那组输出（`intent / adjust_dir / adjust_step / change_bait / change_layer / is_drift / refill_nest / change_spot / urgency / next_action`）映射到**恰好一个** `FishingAction`；`is_drift`、`missing_info` 这类只作为前置条件（走水时不允许建议调漂），不直接变成动作。出钓前那组（`go_or_not / likely_layer / bait_flavor`）走 B 组，输出的是“计划”而非“调整”。

### 6.5 验收（原 V2.0 第 17 节，保留）

- [ ] 输入 `t0 / t / w / d`，正确算 `B` / `d1 / d2 / d3`
- [ ] 正确判断 灵 / 不灵不钝 / 钝 / 铅坠触底
- [ ] 20 基础 + 10 边界 + 10 异常 + 10 真实钓组，共 **50 用例通过**
- [ ] `d1 < 0`、`t0 < t`、`w = 0` 等异常有明确错误
- [ ] 所有核心函数无 UI、无 Jev、无网络依赖

> **50 用例通过前不进入 Studio 面板。**

## 7. `FishSim`：钓场数字孪生（原 2D/3D 沙盒的底层）

原 V2.0 把 2D 沙盒当“教学工具”。插件化之后它顺带变成**评测环境**——这是整个计划里最值钱的一个改动。

### 7.1 三层

```text
FishingState        纯状态（公式算出钩饵位置、底承重、灵钝）
     ↓
LayoutModel         浮漂 / 铅坠 / 上钩 / 下钩 / 上饵 / 下饵 的位置（唯一真相）
     ↓
FishSim 行为         鱼口模型：state → 咬钩概率 → 漂相 / 空竿 / 上鱼
     ↓
Studio 视图         2D 剖面 → 3D 场景（都只读 LayoutModel，不自算）
```

### 7.2 确定性约束（照 `world-kernel` 的规矩）

- 随机只来自 `ctx.rng`，禁止 `Math.random()` / `Date.now()`；
- 同种子两次运行比对指纹；
- 位置是“时间 + 状态”的纯函数，可 `seek()`；
- 新增状态进 `WorldSnapshot`（含 `rngState`），否则回放分叉。

### 7.3 为什么这一步不能省

没有 `FishSim`，闭环只能靠本人去水边跑，一天几十竿，样本积累以月计。有了它：

- 离线跑几千局，秒级出结果；
- 真实 👍/👎 记录作为校准数据，反过来校准模拟器；
- 工厂阶段同构：先仿真、后真线。

**2D 剖面是 `FishSim` 的一个视图，不是另一套逻辑。**

## 8. Jev：`Judge` 的一个实现

### 8.1 契约

```ts
// 规则基线
export const ruleJudge: Judge<FishingState> = { id: 'rule', judge: ... };
// Jev
export const jevJudge: Judge<FishingState> = { id: 'jev', judge: ... };
```

两者**同端口**，所以“规则 vs Jev 谁更适合这个问题”是可跑、可量、可回放的对比，而不是讨论。

### 8.2 Jev 输入

```text
用户原话 + 当前钓组 + Fishing Core 计算结果 + 天气/水情 + 最近几次用户反馈
```

控制 state 大小，不发送完整历史事件流。

### 8.3 输出必须过 Policy

一次请求返回一组独立判断（原 P3），但**只有经过 `Policy` 夹取的那一个才变成 Decision**。越界、字段不适用、置信度过低 → 降级为 `OBSERVE`。

### 8.4 置信度是契约，不是阈值 TODO

初始可以照 V2.0 用 `>=0.85 照做 / 0.60~0.85 试试 / <0.60 继续观察`，但**每一档都必须有对应的校准表**（见第 9 节）。说 80% 的时候真实命中率就该接近 80%；否则置信度只是装饰。

## 9. 反馈与校准（替换 V2.0 的 👍/👎 计数）

原 V2.0 第 10.1 节明确写“这不是严谨的模型准确率，只是产品反馈信号”。产品上没错；但你要研究的正是“决策准不准”，所以补三个字段，让埋点升级成**评测数据集**。

```ts
{
  decisionId, methodId, decisionType,
  confidence,          // 新增：置信度，用于校准
  predicted,           // 新增：预期结果（口变多 / 空竿减少）
  stateSnapshot,       // 新增：决策时的状态（或 stateHash + 精简摘要）
  inputHash, result, feedback, timestamp,
}
```

### 9.1 校准表（`decision-core/calibration.ts`）

```ts
type CalibrationTable = {
  methodId: string;
  buckets: { lo: number; hi: number; decisions: number; succeeded: number }[];
};
```

- 按 `methodId`（规则 / Jev）分开统计；
- 样本少时如实显示“样本不足”，不假装准确；
- 决策前后配对：记 `stateSnapshot`，否则分不清“这次变好”是调整生效还是鱼进窝。

## 11. Studio 插件切换（本版重点）

### 11.1 现状：不支持

| 位置 | 现状 | 影响 |
| --- | --- | --- |
| `studioSession.ts:127` | 写死 `host.install(logisticsPlugin)` | 只有一个插件能装 |
| `studioSession.ts` 同处 | 场景写死 `buildCenterScene(CENTER_PARAMS)` | 场景与插件绑死 |
| `PluginsPanel.tsx` | 只读列表 | 无装卸入口 |
| `TwinViewport.tsx:53-61` | `TABS` 静态 | 插件面板 `PanelDescriptor.component` 没被解析成组件 |
| `TwinViewport.tsx:68/149` | `session` 已是可替换信号、已有 `replaceSession()` | **地基已具备** |
| `PluginHost` | 支持多插件、`uninstall`、`listByCapability` | 宿主侧已具备 |

一句话：**SDK 支持，宿主写死。**

### 11.2 硬约束：切换 = 重建会话，不能热插拔

- `TwinWorld` 在构造时捕获 `behaviors`；
- `replay_sessions.pluginLocks`（`storage-contracts`）说明插件集是回放输入的一部分；
- 热插拔行为会让“同场景 + 同 seed + 同插件锁”复现不出同一串事件。

所以 UI 上“切换插件”的语义必须是：**停表 → `replaceSession()` → 用新插件集重建世界/录制器/时间轴**。

### 11.3 改造清单

1. **插件目录** `apps/studio/src/plugins/catalog.ts`：
   ```ts
   export interface PluginEntry {
     id: string;
     plugin: TwinPlugin;
     /** 该插件能独立提供的默认场景（领域包才需要）。 */
     buildScene?: () => TwinScene;
     /** PanelDescriptor.component → 组件。 */
     panels?: Record<string, Component>;
   }
   export const PLUGIN_CATALOG: PluginEntry[] = [logisticsEntry, fishingEntry];
   ```
2. **`StudioSession` 去硬编码**：构造函数改为 `(plugins: readonly TwinPlugin[], scene?: TwinScene, storage?)`；场景解析优先用传入 `scene`，否则用“领域包插件”的 `buildScene()`。删除对 `logisticsPlugin` / `buildCenterScene` 的直接 import。

## 16. Jev 接入（依据 TypeSafe / OpenRouter 官方文档）

> 来源：TypeSafe 博客《Introducing System One Models & Jev》、OpenRouter 的 Jev 文档与教程、`jev-ai/jev-agent-skill`（已安装到 `~/.agents/skills/jev-agent`）。

### 16.1 Jev 是什么（决定代码怎么接）

Jev 是 System One / 决策模型，**不是聊天模型**：

- 输入：`state`（文本或 JSON）+ 一组 **typed questions**；
- 输出：**typed answers + 概率**，没有自由文本、没有 reasoning trace；
- 三种 primitive：

  | Primitive | 回答什么 | 返回 |
  | --- | --- | --- |
  | **Choice** | 选项里选哪一个 | 选中项 + 每项概率 + confidence |
  | **Noul** | 条件是否成立 | P(yes) |
  | **Score** | 落在有序刻度哪一档（<=10 档） | 概率加权位置 + 每档概率 + confidence |

- 模型 `typesafe/jev-1.13`，32k context，输出 token 免费；调用很便宜。

**官方明确的"不要用 Jev 做的事"**：写文案、生成代码/解释、精确查询、**算术**、鉴权、纯确定性规则、最终权限。

### 16.2 这直接决定了三条代码纪律

1. **数值比较永远不进 Jev。** 底承重 `B`、灵钝分区、空竿率全部在 `fishingCore.ts` 与本地代码里比较完，Jev 只看到类别（`zone` / `empty_hook_rate: low|medium|high`）。`toJevRequest()` 的输出里**不允许出现原始数值字段**，这条有测试守着。
2. **选项由代码定死。** Choice 的 options 就是 `FISHING_ACTION_IDS`；提问与选项都在代码里，Jev 只负责选。选中结果经 `actionFromChoice()` 收敛回封闭动作空间，**再过现有 `Policy` 校验**，越界就降级成 fallback。Jev 的输出永远只是"提议"。
3. **Jev 不生成用户文案。** 解释仍走第 10 节的模板层；Jev 只产出 `action / confidence / reasonCode`。

### 16.3 一次请求三问（对应 P3）

`packages/plugins-fishing/src/jevQuestions.ts`：

```text
state   { zone, hook_state, bait_state, intent, drift, empty_hook_rate, target_fish }
choice  next_action   -> FISHING_ACTION_IDS
noul    needs_observe
score   urgency       -> none | low | medium | high
```

### 16.4 中文

- `JEV_LANGUAGE=zh-CN`：控制提问措辞与交互语言；
- `prompt` 用中文，但 **answer 里的 action id 保持英文**——它是与动作空间对齐的稳定标识，不该随语言变；
- 用户可见文案仍是中文模板，不交给 Jev。

### 16.5 密钥与位置

```text
JEV_API_KEY        必填，只在服务端 / edge；绝不要进前端 bundle、源码、日志或 markdown 示例
JEV_LANGUAGE       可选，zh-CN
JEV_API_BASE_URL   可选，默认 https://thejevai.com
JEV_MODEL          可选，默认 typesafe/jev-1.13
```

`JevJudge` 是 `Judge` 端口的适配器（`plugins-fishing/src/judges/jev.ts`），**不进 `decision-core`**：内核不认识网络，Jev 可换成任何别的实现。规则 Judge 与 Jev Judge 分开跑 `buildCalibration`，"谁更可信"是量出来的。
