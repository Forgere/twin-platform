# Twin Platform：让仿真场景像代码一样可验证

> 对外传播素材（可直发）。所有数字与命令均已跑通，见文末「实证」与 `bun scripts/demo-evidence.ts`。
> 仓库 <https://github.com/Forgere/twin-platform>；在线演示 <https://twin-scene.forgere123zw.workers.dev>。

## 一句话

**Playwright for simulation scenes** —— 不改你的仿真引擎，给场景套一条能进 CI 的断言链：跑一次 → 出 trace → 跟黄金基线比 → 分歧即红灯。

如果你做的是数字孪生 / 工业仿真，下面三类问题大概都遇到过：

1. **改完参数不知道有没有回归。** 演示能过 ≠ 没坏。缺的是一条能进 CI 的断言。
2. **指标比模型更容易骗人。** `parcel:exit` 在单向产线是出货，在**环线上只是绕圈**；末值 backlog 看不见中途爆仓；固定窗口会把慢周期设备判成"没差异"。口径不写清楚，数字就是装饰。
3. **回放靠不住。** RNG 多消耗一次、插件异步 `activate`、事件顺序不稳定——任何一处都会让回放或 CI 全废。确定性不是卖点，是底线。

Twin Platform 只负责"场景质量契约"这一层：版本化场景格式 → 固定步长执行 → 事件 trace → 不变量断言 → 差分定位 → HTML/JUnit 证据。它不是一个渲染器，也不替换行业仿真器。

## 四件事，每句都有证据

### 1. 跨 OS 确定性：同一份代码同一颗种子，逐字节复现

时间只走固定步长（`step(dt)`），随机只来自注入的 `ctx.rng`，内核禁止 `Math.random()` / `Date.now()`。遍历顺序固定即契约。

`examples/packages/hello` 是无随机、无渲染的最小场景。同 commit、同 `--seconds 2`，在 Linux 与 Windows（`ubuntu-latest` / `windows-latest`）上跑出的 `eventHash` / `stateHash` 完全一致——CI 的 `determinism` job 就是为这个而设。

```text
场景 hello-package · seed=1 step=1/60 steps=120
哈希 scene=f1a9680b event=741638a5 state=d3331c98
不变量 1 条：通过 1 / 失败 0 / 异常 0
基线一致（524ff35f）
```

### 2. 故障注入：改了一条事件还声称"复现通过"，门禁照样抓住

仓库自带 [`examples/fault-injection/`](./examples/fault-injection/README.md)：以黄金 trace 为源，只把 `/events/2/payload/status` 从 `idle` 改成 `busy`，**故意不重算** `eventHash` / `stateHash`——这就是伪造证据的典型形态：改了内容，忘了重算指纹。

```text
基线分歧：/events/2/payload/status（value）
```

门禁不靠"内容看着像"，靠**本端重算哈希**：`bun run scene verify` 用 TypeScript 把 trace 重新规范化、重算指纹，声明值与重算值对不上就直接红灯。篡改那份的 JUnit 里 `firstDivergence` 就是这一处 pointer，报告 HTML 也内嵌同一处分歧——可以直接拿去做评审，而不是让人信一张截图。

### 3. 换引擎不换门禁：SimPy / FMU / OpenSCENARIO 同吃一套 verify

外部 runtime 不自证。它们产出**同一套 trace 结构**，`bun run scene verify / diff / report` 用本端逻辑重算哈希、比对基线：

| Runtime | 怎么来的 | verify 重算 |
|---|---|---|
| SimPy 4（`adapters/simpy`） | Python 真实跑离散事件模型 | `event-hash` 声明 = 本端重算 |
| FMI 2.0 FMU（`adapters/fmu`） | `ctypes` 加载真实 FMU 二进制 | 同上 |
| OpenSCENARIO 1.x（`adapters/openscenario`） | 导入 ASAM OpenSCENARIO 子集并执行 | 同上，且 `diff` 对齐基线 |

这意味着：你可以把仿真核心换成任一支持该 trace 契约的引擎，验证链一行都不用动——**门禁锁的是证据契约，不是内核**。

### 4. 场景包一键跑：输入 + 断言 + 基线全在一个目录里

一个 scene package 固化一次可验证运行所需的全部输入：

```text
<package>/
  scene.json          版本化场景
  plugins.lock.json   插件锁（不是"我本地装的那个版本"）
  seed.json           seed / step / 时间网格
  actions.json        外部动作脚本
  invariants.json     该验什么（挂了 check 就真跑）
  expected/trace.json 黄金基线
```

`bun run scene audit --package <dir>` 一次带齐，并真跑包里挂的不变量。例子是 [`examples/community/mini-line`](./examples/community/mini-line/README.md)——一条**环线**：

```text
场景 community-mini-line · seed=1 step=1/60 steps=1800
哈希 scene=9c00f9f6 event=75856de3 state=80e4600a
不变量 2 条：通过 2 / 失败 0 / 异常 0
报告 PASS
基线一致（762d489a）
```

两条断言抓的是真实口径造假：

- `logistics.line.loop`：包裹绕完一圈会先 `parcel:exit` 再 `parcel:enter`，把 `exit` 当吞吐量的看板就栽在这里——断言 `exit == enter − 1`（仍在环上）。
- `logistics.line.no-teleport`：包裹必须沿闭环路径连续运动（`loop === repeat`、弧长不越界、速度非负）。

把包裹的 `motion.loop` 从 `repeat` 改成 `clamp`，CLI **立刻 exit 1 并指名是哪一个包裹**。

闭环中心的 `logistics.center.flow` / `logistics.center.conservation` 现在也是可挂的内置 id——
但它们是**从 `plugins-logistics` 借来的引用**（与 Studio 审计面板同一份对象），不是 CLI 里抄的副本，
所以「CI 里挡你的」和「页面上看到的」永远同一个口径。

## 为什么是现在，为什么是你该看一眼

- 仓库 24 个包、`bun run test` 629 项全绿、类型检查全绿、`scene` CLI 可打成单文件 `npm i` 即用。
- 参考插件覆盖物流闭环（产出 → 打包 → 入库 → 出库 → 卡车运走，含物料守恒）与台钓（种子化随机、合法钓组几何、动作效果可复现）——同一套纪律跑得通两个域，新插件就有清晰契约。
- Studio 三维视口是**展示层**（看场景、播回放），不是验证链入口；验证靠上面的 `bun run scene`。

## 实证

- 一条命令跑完上面四件事：`bun scripts/demo-evidence.ts`（证据落 `./demo-evidence/`，纯 bun 部分加 `--only core` 不依赖 Python）。
- 故障注入演练：`bun examples/fault-injection/check.ts /tmp/fi`（12 项 PASS）。
- 跨 OS 确定性：CI `determinism` job（`ubuntu-latest` + `windows-latest`）对齐 `examples/packages/hello` 等黄金基线。
- 全文数字来自 `bun run scene audit --package examples/packages/hello` / `examples/community/mini-line` / `examples/packages/logistics-center`。

## 不讲什么

边界比定位更重要——这些是别人的活，我们不撞：通用数字孪生平台（Ditto / FIWARE / Azure Digital Twins）、"确定性内核"当主卖点（Ananke / Chronos / Paracosm）、3D 资产互操作（OpenUSD / SimReady）、动态模型封装接口（FMI / FMU 我们**接**它，不重做它）。
