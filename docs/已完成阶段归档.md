### 阶段 G：货架存取（先入先出）与可点选托盘

**问题**：货架上的托盘是"烘焙"进 `buildAsrsRack` 模型里的装饰件（按确定性哈希摆几块）。
结果是点不中、也不在物料列表里，数量永远不变——因为货架压根没有取放货逻辑，
`asrs-cycle` 只是让堆垛机空跑一个时间函数。

**做法**：把托盘变成真正的实体，并给货架补一套最小的库存语义。

| 能力 | 落地位置 |
| --- | --- |
| 托盘是实体 | `devices.ts`：`pallet(id, position, { label, color, carrier })`；`carrier` 声明它归哪台堆垛机管 |
| 货位声明 | `devices.ts` 的 `asrsRack` 新增 `levelHeights` / `bays` / `craneId` / `side`——货架横梁高度、堆垛机取货高度、托盘落位高度共用同一份数组 |
| 托盘池 | `template.ts`：每条巷道生成一池托盘（默认 6 块，上限 = 入库队列能排下的块数，由 `palletPoolCapacity()` 算），初始排在 L 形载货站台上。**注：阶段 H 把固定托盘池换成了打包站动态产出，这一行只描述当时的状态** |
| 库存语义 | `asrs.ts` 重写 `asrs-cycle`：托盘五态状态机 `queued → carrying-in → stored → carrying-out → outbound → queued`，**先入先出**：入库挑第一个空货位并打 `seq`，出库取 `seq` 最小的一块 |
| 队列 | 队列按 `order` 排队、沿站台折线按弧长滚动（`qpos`），节距 0.9m；出库托盘等 `1.1 × cycle` 后回到队列尾（`recycle` 模式；阶段 H 的中心场景改用 `shipped`，由卡车运走） |
| 可点选 | 托盘走 `CargoPool` 实例化池，拾取与选中解析本来就用同一张全量表，所以立刻就能点中；货架模型不再烘焙托盘，只画立柱 / 每层横梁 / 层板 |
| 看得见的状态 | 货架 `attrs.used/capacity`、堆垛机 `attrs.task/stock/nextOut`；检视面板新增实时状态行（`entityState.ts` 纯函数，可单测），HUD 增加"立库库存 X/Y" |

**确定性**：位置是"本圈任务 + 时间"的纯函数；任务与库存只写在 attrs 里（快照覆盖），
每圈只决策一次；不碰 `ctx.rng`、不读挂钟。快照恢复后继续跑与一路跑到底逐位一致（有测试）。

**当时的限制（阶段 H 已解决）**：内核的 `BehaviorContext` 没有 `spawn` / `despawn`，
所以托盘池是**闭环**的——出库托盘等一会儿回到入库队列尾，语义上相当于"外部取走 + 新托盘到货"。
阶段 H 给内核补上了 `spawn`/`despawn`，中心场景的托盘改由打包站产出、卡车运走；
`recycle` 模式仍然保留，`asrs.test.ts` 用自建最小场景继续验证它。

**测试**：`asrs.test.ts`（7 个用例）逐帧盯状态迁移——入架序号单调、出库永远取最老的、
入库取队列头、托盘落在声明层高上且同组不重叠、占用 attrs 与已上架数一致、
同种子两遍一致、快照恢复后一致、五个状态都出现过（环路跑得通）。
`apps/studio` 的 `entityState.test.ts`（6 个用例）覆盖检视面板的文案翻译
（写这个测试当场抓到一个 bug：货位键是字符串，`层/列` 没转数字，永远显示"第 1 层"）。

测试：`bun test packages` 177 个用例全绿（+22），`apps/studio` vitest 7 个用例全绿。

### 阶段 H：在「智能物流中心」场景上改造出闭环产线

**需求**：一处持续产生小货物 → 小货物沿线运行 → 2 个小货物打包成 1 个大货物 →
大货物进立库 → 立库用卡车运走，形成闭环。要求**改造原场景**（`logistics-center`），
而不是另起一个新场景；这条链路还要能**被检验**，不是"看着像在跑"。

**卡点**：内核的 `BehaviorContext` 原来只有 setAttr / setStatus / setTransform / move / emit，
**没有生成与销毁实体**。所以"一处产生"和"被消耗掉"都表达不了——旧版 `packing.ts` 的注释里
就写着这个限制（只能给经过工位的小货物打个 `boxed` 标记）。这一阶段先把这块补上。

| 能力 | 落地位置 |
| --- | --- |
| 行为可生成 / 销毁实体 | `world-kernel`：`BehaviorContext.spawn(entity)` / `despawn(id)`；id 必须由行为按确定性规则派生（计数器存 attrs，随快照恢复）。本步生成的实体下一步才进 `ctx.entities` |
| 快照保真 | `WorldSnapshotEntity.declaration`：**运行时生成**的实体带完整声明（能力/外观/配置/路径），`restore()` 按声明重建；场景里声明的实体仍从 scene 重建，快照不膨胀 |
| 回跳不留幽灵 | `restore()` 计算"恢复前 vs 恢复后"的实体差集写进 `added`/`removed`；`restoreFrom()` 不再清空差量——否则往回 seek 之后，上一时间线生成的小货物会一直留在场景里 |
| 实体状态带外观 | `WorldEntityState.visual`：渲染层补运行时实体的模型时要按声明画（否则生成的货物一律是默认方块） |
| 小货物发生器 | `devices.goodsSource` + 行为 `goods-source`：按 `interval` 生成小货物，沿**主环线**跑（一路经过两个质检站与分拣支线）；**在制达到 `maxWip` 就停产**（背压，否则场景会被塞爆） |
| 打包站 | `devices.packingStation` + 行为 `packing`（重写）：两台龙门工位骑在主线上（x=6 / x=14），经过的**发生器产出**的小货物被扣进缓存位（`attrs.heldBy`），凑够 `batch` 个一起 `despawn`，`spawn` 1 个托盘 |
| 立库接料 | `asrs-cycle`：托盘 `state='conveying'` 时沿**托盘自己 config.path** 走向队列尾（刻意不给它 motion——内核每步都会把带 motion 的实体拉回路径终点，和货位/出库带上的位置打架），到队尾转 `queued`；`attrs.queueFree` 供打包站背压 |
| 出库与装车 | `asrs-cycle` 新增 `outfeedX` / `outboundMode: 'shipped'` / `highWater`：库存到高水位就转出库，出库托盘落到**出库缓存台**（`dock-a` / `dock-b`）；行为 `truck-cycle` 在缓存台旁装车（真正 `despawn`），装满或等够 `dwell` 就沿一条**不压任何皮带**的路线驶离，`awayTime` 后回场 |
| 场景改造 | `centerTemplate`：删掉预置的 10 个 `parcel-*` 与 12 块固定托盘池；新增发生器 ×1、打包站 ×2、出库缓存台 ×2、卡车 ×2；旧"入库接驳环线"（`belt-io-*-in`、两台入库移栽机）撤掉，换成本巷道自己的**打包出料带**（东行 → 北上 → 西行插进队列尾），主线接驳段同步延长补缺口 |
| 工作台 | 场景仍是 `logistics-center`；HUD 改为在制小件 / 已产出 / 已打包 / 已运走 / 在制托盘 / 立库库存 + 两台卡车状态；实体列表改为"场景声明 + 运行时生成"的合并视图（点得中生成的货物）；方案对比改为"2 合 1 vs N 合 1 打包"，两条方案跑同一组行为 |

**布局**（改造后，一个巷道为例）：

```
  小货物发生器 ──主环线（过质检/分拣）──> 打包站(2 合 1) ──出料带──> 载货站台队列尾
                                                                        │
                                        卡车装车离场 <── 出库缓存台 <── 堆垛机存/取 <── 货位
```

出库缓存台与卡车都摆在**主线与载货站台之间的皮带走廊外侧**（A 巷道在西、B 巷道在东），
路线先沿走廊开出场地再北上离场——这段走廊里没有任何皮带，卡车才开得出去。

**测试**（这一阶段的重点就是"可检验"）：

- `closedLoop.test.ts`（9 个用例）：四个环节都在场景声明里；整条线跑通（产出/打包/入库/出库/运走都有事件）；
  **打包是严格 2 合 1**（每次消耗 2 个不同的、已产出的、且当场消失的小货物）；
  **物料守恒**（小货物 = 2×打包 + 在制；托盘 = 已运走 + 在系统里）；背压不超 `maxWip`；
  卡车每趟 1..capacity 件且装走的托盘真的消失；货物全程贴着皮带/货架（被货叉抬着、被缓存位扣住的除外）；
  同种子两遍事件流与实体指纹逐位一致；快照恢复后生成出来的货物与托盘都能按声明重建。
- `pallet-flow.test.ts`（原"料应进入堆垛机而非倒回"的回归测试）改为跟踪**动态产出的托盘**：
  连续 queued 段内 `qpos` 单调不增、出入库事件都发、托盘都进过货位、至少一批走完
  "入库 → 出库 → 被卡车运走"。
- `layout.test.ts`：center 场景的皮带不叠面、小货物路径每个拐点都有皮带、
  两条打包出料带端点都有皮带、出库缓存台不压任何输送线。
- `world.test.ts` 新增 5 条：spawn/despawn 进世界与差量、声明随快照恢复、
  快照恢复后继续跑一致、**回跳时消失的实体出现在 removed 里**、重复 id 抛错。
- `asrs.test.ts` 改为**自建最小立库场景**（一条巷道 + 两排货架 + N 块预置托盘）：
  行为语义几秒钟就能验完，不再依赖中心场景里几分钟才产出的托盘。
- `apps/studio`：`studioSession.test.ts` 不挂 WebGL 直接推世界读遥测（HUD 那几个数对不对）。

测试：`bun test packages` 全绿，`apps/studio` vitest 9 个用例全绿。
