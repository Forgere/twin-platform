# 开源方向与行动计划：可验证仿真场景（Verifiable Simulation Scenes）

> 本文档是 twin-platform 对外开源的**战略定位与落地行动计划**单一入口。
> 内部技术路线图见 [行动计划](./行动计划.md)；本文聚焦"开源该讲什么、不该讲什么、下一步怎么走"。
> 最近更新：2026-11-01。

## 0. TL;DR（一句话定位）

> **让仿真场景像代码一样可测试、可回放、可审计、可进 CI。**
> 对外类比：**Playwright for simulation scenes。**

`twin-platform` 现有的 `world-kernel`、工厂插件、钓鱼插件不是三个产品，而是**同一套基础设施的三种证据**：
`world-kernel` 是参考运行时，工厂与钓鱼是两套跨领域 **conformance suite**。

---

## 1. 现状与问题

我们已具备：

- `scene-schema`：版本化场景 JSON、校验、迁移、结构化编辑 ops
- `world-kernel`：固定步长、种子随机、事件序列、快照/恢复、seek、外部数据混合模式
- `plugin-sdk`：manifest、能力声明、配置 schema、插件锁、同步 activate、行为隔离
- 工厂插件：工业物流不变量（物料守恒、不脱线、设备运动、事件口径）
- 钓鱼插件：随机行为不变量（漂相权重、动作落地、链序、空间关系、RNG 消费纪律）
- evals / audit：用户故事验收、静态审计、行为审计、ASCII 证据
- JEV 实测：场景 patch、指标口径、观察窗、沉默旋钮、候选组合与回放留痕

**问题不在内容不够，而在于三个 demo 共用的底层价值没被命名。**

如果对外分别讲"工厂孪生"和"钓鱼模拟"，别人会把我们当成两个互不相关的应用；真正能形成开源心智的，是它们背后那套"**场景如何被描述、执行、验证、回放**"的基础设施。单独把 `world-kernel` 开源，也只会被当成"又一个 deterministic core"，缺乏锐度。

## 2. 明确不做（边界）

| 不做 | 原因 |
| --- | --- |
| 通用数字孪生平台 | 会撞 Eclipse Ditto / FIWARE / Azure Digital Twins / Omniverse / 各类 IoT dashboard；需要 connector、权限、部署、UI、行业模型，开源维护成本极高 |
| 把"确定性仿真内核"当主卖点 | Ananke、Chronos、Paracosm 已在讲 deterministic kernel / replay / fork / artifact / snapshot；单独拿出来没有足够锐度 |
| 一开始做 LLM 世界模型 | LLM 可作为后续 adapter（生成场景 patch → runner 验证 → 输出审计报告），但不先把项目说成"AI 自动生成数字孪生"，否则先被质疑幻觉、稳定性与数据安全 |
| 先做标准组织式规范 | 不要先写大标准再找人实现。正确顺序：自己的 runtime 跑通 → 两个插件跑通 → 抽公共 `.scene`/`.trace`/`.audit` 格式 → 接一个外部引擎 adapter → 最后才叫 spec |

---

## 3. 推荐方向：可验证仿真场景基础设施

我们要占的不是"数字孪生"，也不是"世界模型"，而是：

> **仿真场景的质量保障与回归基础设施。**

它独立于渲染器、行业仿真器和 LLM，回答这些问题：

- 这个场景到底声称自己会做什么？
- 哪些动作真的生效了，哪些是 no-op？
- 哪些指标口径有效，哪些指标在骗人？
- 同种子、同插件版本、同输入，结果是否逐字节一致？
- 如果变了，第一处分歧在哪（JSON Pointer）？
- 这个插件是否满足宿主要求的确定性纪律？
- 这次改动能否进 CI 门禁？

## 4. 生态缺口判断

| 方向 | 代表 | 解决什么 | 没解决什么 |
| --- | --- | --- | --- |
| 数字孪生后端 | Eclipse Ditto | 设备状态、权限、API、消息 | 仿真执行、行为验证、场景回归 |
| 3D 场景组合 | OpenUSD / SimReady | 资产、几何、物理属性、3D 互操作 | 轻量行为场景、事件轨迹、业务断言 |
| 模型交换 | FMI / FMU | 动态模型封装、联合仿真、时钟事件 | 场景生命周期、指标口径、行为审计、CI |
| 汽车场景标准 | ASAM OpenSCENARIO | 驾驶动态场景描述 | 通用工业/游戏场景；官方也说明跨仿真器结果不必一致 |
| 工业 DES | SimPy、JaamSim、TwinOps | 排队、资源、瓶颈、吞吐 | 跨引擎场景验证、回放差分、插件合规 |
| 确定性内核 | Ananke、Chronos | 可复现执行、replay、failure capsule | 数字孪生场景语义、行业插件、审计报告 |
| LLM 世界模型 | Paracosm、AgentWorld | 反事实分叉、agent 决策、世界推演 | 严格工业时序、资源约束、可验证行为 |

**缺口不是"没有仿真器"，而是缺少一个独立于渲染器、行业仿真器和 LLM 的轻量场景质量契约。**

## 5. 开源产品形态（暂名 SceneCI，先不急着发明"标准"）

### 5.1 Scene package（可执行场景包）

```text
scene.json          # 场景声明
plugins.lock.json   # 插件 id + version + config hash
seed.json           # 种子、步长、观察窗
actions.jsonl       # 用户或 agent 动作
invariants.json     # 不变量
metrics.json        # 指标与口径
expected/           # 黄金基线
```

重点不是描述全世界，而是把一次可验证运行所需的输入锁死。

### 5.2 Headless runner（CLI 是第一公民）

```bash
scene run ./factory.scene
scene audit ./factory.scene
scene replay ./run.trace.jsonl
scene diff baseline.trace current.trace
scene sweep ./factory.scene --seeds 1..100
scene report ./run --html
```

3D Studio 只是可选 adapter，不是项目核心。

### 5.3 Evidence artifact（每次运行产出可分享证据）

- canonical trace JSONL
- event hash / scene hash / plugin hash
- first divergence JSON Pointer
- invariant violations
- metric definitions 与 metric values
- observation window 是否足够
- silent action / silent knob 检测
- HTML 审计报告
- JUnit XML，可直接进 CI

### 5.4 Plugin conformance kit（插件不是"能跑就行"，必须证明）

- 不调用裸 `Math.random`
- 不直接读 wall clock
- 不异步 activate
- 不绕过内核改状态
- 所有动作要么有事件，要么明确 no-op
- 同插件锁 + 同种子可以回放
- 崩溃不会拖死宿主
- manifest 声明的能力与实际注册一致

这会让 `plugin-sdk` 从"内部模块化工具"变成真正的社区基建。

## 6. 两个现有插件的角色

### 工厂插件：证明"工业物流不变量"

作为严肃工业示例：

- 物料不凭空产生、不丢失
- 物料不脱线
- 堆垛机状态、层高、位置语义正确
- 事件口径区分"绕圈一次"与"真实出货"
- 高水位、在制上限、节拍 patch 可比较差分
- 观察窗不足时主动警告，而不是输出假结论
- 沉默旋钮会被标记为"本场景不可观测"

### 钓鱼插件：证明"随机行为也能被验证"

作为很好的传播 demo（比工厂更容易被普通开发者玩起来）：

- 静水中不允许出现移漂
- 走水时移漂权重必须上升
- 钓组链序合法
- 饵不离钩
- 每个动作必须产生状态变化或明确 no-op
- 一次 weighted choice 只消耗一次 RNG
- 同种子漂相序列、咬钩时间、提竿窗口逐位一致

一个严肃、一个有趣，组合很有辨识度。

## 7. 仓库重组建议

建议从当前 monorepo 中抽出一个新的开源核心，明确分层：

```text
scene-ci/
  packages/
    scene-spec/          # 场景、动作、指标、断言、trace 类型（不依赖内核）
    scene-runner/        # headless 执行、回放、差分
    scene-audit/         # 不变量、静态审计、行为审计
    scene-plugin-kit/    # 插件 manifest、锁、conformance tests
    scene-cli/           # run/audit/replay/diff/report
    twin-runtime/        # 现有 world-kernel，作为参考实现
  examples/
    logistics-factory/
    fishing-lab/
  adapters/
    three/               # 可选
    simpy/               # 后续证明不只服务自己
  docs/
    positioning.md
    plugin-contract.md
    determinism.md
    metric-semantics.md
```

关键原则：

- `scene-spec` 不依赖内核；
- `scene-runner` 可以接别的 runtime；
- `twin-runtime` 是第一个 reference runtime；
- 工厂与钓鱼是 reference plugins；
- 3D、数据库、MQTT、LLM 都是 adapter。

> 注：当前仓库 `twin-platform` 已是这一结构的雏形（world-kernel / scene-schema / plugin-sdk / plugins-logistics / replay-core / analytics-core 均齐备），对外叙述只需把重心从"平台"转向"验证基础设施"，不必立刻物理拆分。

## 8. 第一版 MVP 范围

第一版只做这条闭环：

```text
加载场景
→ 锁定插件和配置
→ 固定 seed 运行
→ 收集事件和指标
→ 执行不变量
→ 输出 trace + report
→ 与 baseline diff
→ CI pass/fail
```

**第一版不做**：完整 Studio、在线协作、云数据库、可视化大屏、自动优化、LLM 场景生成、多语言 SDK、插件市场。这些会稀释焦点。

## 9. 传播叙事

不靠"我用了 Three.js / Solid / 3D"，而靠一句很痛的工程问题：

> **你的数字孪生看起来会动，但你能证明它没骗你吗？**

连续写四类内容：

1. **确定性不是卖点，是底线**
   - 一个 RNG 多消耗一次，回放全废；
   - 一个插件异步 activate，插件锁全废；
   - 一个事件顺序不稳定，CI 全废。
2. **指标比模型更容易骗人**
   - `parcel:exit` 在单向产线是出货，在环线只是绕圈；
   - 末值 backlog 看不见中途爆仓；
   - 300 秒窗口会把慢周期设备判成"没有差异"。
3. **动作必须可审计**
   - 调参没效果不等于代码没执行；
   - 要区分"无效改动"与"本场景沉默旋钮"；
   - no-op 必须显式声明。
4. **跨领域 conformance**
   - 同一条验证纪律既能查工厂输送线，也能查钓鱼漂相；
   - 这证明我们不是做了一个垂直 demo，而是一套基础设施。

## 10. 验收指标（不要一开始看 star）

- 5 分钟内：`clone → install → run factory → 得到 HTML 审计报告`
- 同 commit、同 seed，在 Windows / Linux 下 trace hash 一致
- 故意注入一个 bug，report 能指出第一处 divergence
- 工厂和钓鱼两套插件共享同一套 runner / audit / report
- 外部开发者不看内核源码，也能写出一个合规插件
- 至少有 1 个外部 runtime adapter，证明不是自嗨
- CI 里能跑 JUnit 输出并阻断回归
- 社区贡献主要以"规则、场景、adapter"形式出现，而不是都要求改核心

文案已按「工业 / 仿真工程师」口径写进 README 第一屏，改动时守这几条：

   `bun run scene audit --template logistics.center --template-params examples/logistics-center/fast.json --seconds 300`。

3. **「不是什么」比「是什么」先讲。** 边界表（Ditto / Ananke / OpenUSD / FMI）防的是读者把本项目
