# 服务端与持久化

> 一句话：**没有服务端，就没有持久化，也接不了任何实时数据源。**
>
> 此前 Studio 是纯静态站：`storage-postgres` 实现完整、测试齐全，却没有任何运行时代码
> import 它——因为浏览器既连不上 PostgreSQL，也没有文件系统。场景导入靠 File API，
> 刷新即丢。服务端就是补上这一块，同时给 MQTT / OPC-UA 留一个能常驻的进程。

## 1. 快速开始

```bash
bun run dev:server     # 或：cd apps/server && bun src/index.ts
```

默认 `http://localhost:8787`，数据落在 `data/twin.json`。
环境变量：`PORT`、`TWIN_DATA`、`TWIN_STUDIO_DIST`、`TWIN_STORAGE`、`DATABASE_URL`、`TWIN_PG_SCHEMA`。

- `TWIN_STORAGE=file`（默认）/ `postgres`：选后端；
- 设了 `DATABASE_URL` 且 `TWIN_STORAGE` 不是 `file` 时，自动走 postgres；
- `TWIN_PG_SCHEMA`：表前缀 schema（默认空，即 public）。

启动后如果 `apps/studio/dist` 存在，服务端会**同源托管** Studio（含 SPA 回退）；
不存在就只提供 API，开发模式继续跑 vite 即可。

## 2. 架构：三层同一个契约

```
浏览器                        服务端                      存储
┌──────────────┐   HTTP    ┌──────────────┐   接口   ┌──────────────┐
│ storage-http │ ────────► │  apps/server │ ───────► │ storage-file │
│ (fetch)      │           │  (Bun.serve) │          │ (JSON 文件)  │
└──────────────┘           └──────────────┘          └──────────────┘
      │                                                     │
      └─────────── 都实现 @twin-platform/storage-contracts ──┘
                    （六个仓储：scenes/events/snapshots/
                     sessions/state/metrics）
```

`storage-memory`（纯静态兜底）、`storage-file`（默认服务端后端）、
`storage-postgres`（已接线，设 `TWIN_STORAGE=postgres` 即启用）实现的是**同一个 `TwinStorage` 接口**，
换后端只是换一个实例，调用方一行不改——服务端通过 `createServerStorage` 这一个工厂选后端。

| 包 | 位置 | 用途 |
|---|---|---|
| `storage-http` | 浏览器 | 走 fetch 调服务端；**事件攒批**（默认 64 条 / 400ms） |
| `apps/server` | 服务端 | REST API + 静态托管；零外部依赖，后端可切换 |
| `storage-file` | 服务端 | 单 JSON 文件；debounce 落盘 + 原子写（tmp → rename） |
| `storage-postgres` | 服务端 | PostgreSQL；自动跑迁移、自动选驱动（`pg` / Bun 内置 `Bun.sql` / PGlite） |
| `storage-memory` | 浏览器 | 服务端不在时的兜底，刷新即丢 |

## 3. API

全部 `/api/*`，JSON 入出。

### 健康检查
```
GET  /api/health              → { ok, backend, dataPath, scenes }
```
前端靠它判断服务端在不在。**探不到是正常状态**（纯静态部署），不报错。

### 场景
```
GET    /api/scenes                  → SceneSummary[]
POST   /api/scenes                  → 保存场景（服务端会重新校验，脏场景 422）
GET    /api/scenes/:id              → TwinScene | 404
DELETE /api/scenes/:id              → 连带清掉事件 / 快照 / 状态 / 指标 / 会话
```

> 服务端**必须**重新校验场景。前端校验过不代表别人也会，脏场景进库会污染后续所有回放。

### 事件
```
POST /api/events?sceneId=           → 追加事件；sequence 不单调返回 409
GET  /api/events?sceneId=&since=&until=&entityId=&type=&limit=
GET  /api/events/latest?sceneId=    → { sequence }  回放游标
POST /api/events/truncate?sceneId=&sequence=   → 分叉时截断
```

**409 是设计，不是错误**：sequence 不单调意味着调用方在重复回放，
若静默放行，新时间线的事件会接在旧事件后面，回放出来的是两条时间线拼接的假历史。

### 快照 / 会话 / 状态 / 指标
```
POST /api/snapshots?sceneId=              GET /api/snapshots/query?sceneId=&sequence=|&time=
POST /api/sessions                        GET /api/sessions?sceneId=    GET /api/sessions/:id
POST /api/sessions/:id/finish             { duration }
POST /api/state?sceneId=                  GET /api/state?sceneId=
POST /api/metrics                         GET /api/metrics?sceneId=&metric=&entityId=&from=&to=
```

## 4. 事件续写（必须理解）

服务端持久 ⇒ 一个场景第二次被录制时，库里已有上一次的事件。

```ts
const session = new StudioSession(scene, storage);
await session.resumeFromStorage();   // world.resumeFrom(latestSequence)
```

内部走 `EventLog.resumeFrom(sequence)`：**只推进、不回退**，
把"已落库"的游标推到库里的最新值，新事件从它之后开始编号。

不这么做会撞 409；放行则拼出假历史。

## 5. 写入性能

录制器是**每帧**调 `append` 的。若条条发 HTTP，60Hz 仿真就是每秒 60 个请求。
所以 `storage-http` 的事件仓储会攒批：

- 攒够 `batchSize`（默认 64 条）立即发送
- 或等够 `flushMs`（默认 400ms）发送
- 任何**读**操作（query / latestSequence / truncateAfter）前先 flush，
  否则会读到自己刚写却还没发出去的旧状态
- 发送失败时事件**退回缓冲区**重试，不凭空消失

服务端侧同样是 debounce 落盘（250ms）+ 原子写（tmp → rename），
进程退出前 `flush()` 一次，避免最后几百毫秒的数据丢失。

## 6. 换 PostgreSQL

`@twin-platform/storage-postgres` 已实现同一套契约（仓储 + 迁移执行器 + 驱动装配）。
服务端通过 `apps/server/src/storage.ts` 的 `createServerStorage` 这一个工厂选后端，
路由代码（含 `index.ts`）完全无感——切换只是设一个环境变量：

```bash
# 默认（不设置时）：落单 JSON 文件，零依赖
TWIN_STORAGE=file

# 切到 PostgreSQL：连库、自动跑迁移、自动选驱动
TWIN_STORAGE=postgres
DATABASE_URL=postgres://user:pass@host:5432/twin
TWIN_PG_SCHEMA=twin          # 可选：表前缀 schema（默认 public）

# 没装数据库也要验证 Postgres 后端？用 WASM 版真实 PostgreSQL
DATABASE_URL=pglite://memory
```

> 便捷规则：只要设了 `DATABASE_URL` 且 `TWIN_STORAGE` 不是 `file`，
> 就自动走 postgres。所以只设 `DATABASE_URL` 也能切。

`connectPostgresStorage` 内部做了三件事，调用方无感知：

1. **驱动自动选**：优先注入的 `executor` → 否则 `pglite://` 连接串走
   `@electric-sql/pglite` → 否则动态 `import('pg')`（Node 通用）→
   否则用 Bun 内置 `Bun.sql`（`bun run` 起服务端时零依赖连 PG）。
   都找不到就给出明确的安装指引，而不是抛 `Cannot find module`。
2. **迁移自动跑**：连上后执行 `migrations/*.sql`，幂等——每张表 `if not exists`，
   并记 `_twin_migrations` 台账，重跑只补没跑过的。无需手动 `psql`。
3. **探活**：`/api/health` 返回 `backend`、`driver`、`healthy`、`serverVersion`，
   方便确认当前跑在哪个后端。

`apps/server/.env.example` 列了全部环境变量。浏览器侧完全无感——它只认 HTTP。

### 零依赖跑 Postgres 后端：PGlite

机器上没装 PostgreSQL 也能验证"Postgres 后端这条链路"——连接串用 `pglite://`：

```bash
cd apps/server
bun run smoke:postgres                                  # 默认 pglite://memory
DATABASE_URL=postgres://user:pass@localhost:5432/twin bun run smoke:postgres   # 打真实库
```

`@electric-sql/pglite` 是编译进 WASM 的**真实 PostgreSQL**（实测报 `18.3`），进程内内存库，
不需要任何外部服务。冒烟脚本走完整的 `createServerStorage`：建连 → 迁移 → 场景/事件/快照/
状态/指标 CRUD → 级联删除 → 释放连接，11 项检查全过才算通。

两个必须知道的点：

- **必须显式 `pglite://` 前缀**，它绝不会作为 `postgres://` 的兜底——
  内存库静默兜底会把真实连接的数据"写进虚空"。
- PGlite 0.5 对含动态 DDL 的 `$$` plpgsql 函数体（`twin_ensure_event_partitions`）解析有局限，
  迁移时自动跳过它；`twin_events` 已有 DEFAULT 分区兜底，入库与契约都不受影响。

> 运行环境：仓库在 WSL 文件系统里时，**务必用 WSL 内的 bun 跑**（`~/.bun/bin/bun`）。
> Windows 侧 bun 经 UNC 路径看 `packages/*/node_modules` 里的符号链接是断的，
> 会误判成"没装 @electric-sql/pglite"而静默跳过 PGlite 相关测试。

在此之前，`storage-postgres` 一直是"写了但没接线"的状态：
不是它没用，而是**没有服务端就没有它能跑的地方**。现在服务端已经把它接上了。

## 7. 还没做

- **鉴权**：API 全开放，只适合内网 / 本地
- **多租户**：所有场景在一个库里，无隔离
- **迁移到 Postgres**：数据量大时单文件全量重写会成为瓶颈
- **MQTT / OPC-UA Adapter**：✅ 已完成。内核入口 `world.ingestExternalFrame` 已就绪，
  两个协议各实现一份 `ExternalFrameSource`（见 `packages/data-source-mqtt`、
  `packages/data-source-opcua`），并复用 `replay-core` 的 `BufferedFrameSource` 底座与
  `toExternalFrame` 映射。常驻进程示例见 `apps/server/scripts/live-twin.ts`
  （`bun run live:mqtt`）。
