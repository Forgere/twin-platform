# 架构复盘：目标达成度 / 外部系统接入 / 复杂工厂适配

> 核查方式：代码走查 + 运行时取证（`bun test packages` 200 pass / 0 fail、23 个文件；
> `buildCenterScene()` 实跑取实体清单）。每条结论都带文件路径证据。

## 0. 结论速览

| 维度 | 判定 | 一句话依据 |
| --- | --- | --- |
| 最初目标（阶段 A–H） | ✅ **达成** | 计划里 A→H 全部勾完，200 测试全绿，闭环产线（产出→打包→入库→出库→装车）真跑通且有守恒断言 |
| 接入外部系统 | ⚠️ **仅 1/3 接通** | 只有**离线 CSV 文本回放**真能用；MQTT/WS/OPC-UA 零实现；**没有服务端**，Postgres 与实时接入在浏览器里跑不起来 |
| 适配复杂工厂 | ❌ **架构留了缝，实现是演示级** | 场景坐标**硬编码在 TS 函数体**（`aisleXs=[8,16]`），单层米制、45 实体、无 LOD/剔除，无法表达真实厂区 |

一句话：**它是一个完成度很高的"可插拔仿真内核 + 演示场景"，还不是"能接现场、能扛规模的工厂数字孪生平台"。**
内核那层是资产，外面三层（布局来源、协议接入、服务端）都还是空的。

> 一期验收：用物流插件和 CSV/MQTT 数据，在**一天内**建立一条可运行、可回放、可分析的产线场景。

## 2. 接入外部系统

### 2.1 现状地图

```
MES / PLC / WMS ──✂── [协议 Adapter] ──✂── CsvFrameSource ──✅── world.ingestExternalFrame
                  零实现                只有 CSV 一种           唯一入口，纯函数换算
                                                                        │
                                                        ┌───────────────┴───────────────┐
                                                   ✅ 内存仓储                    ✂️ storage-postgres
                                                  （studio 实际用的）              （apps 零 import）
```

### 2.2 三个硬阻断

**阻断一：没有服务端（最致命）**
`apps/studio/vite.config.ts` 未开 SSR，产物是纯静态 `dist/client`；全仓库无 `Bun.serve` / API route / server function。
→ `storage-postgres`（要 Node + `pg` 驱动，而 `pg` 甚至不在其依赖里）、任何长连接协议，**在浏览器里都无从落地**。

**阻断二：只有 CSV 一种 Adapter，且是离线文本**
`data-source-csv/src/parse.ts:153` 入口是 `parseCsv(text)`——读字符串，无文件选择、无网络。
Studio 侧 `DataSourcePanel.tsx:33` 是一个 `<textarea>` 手工粘贴。
全仓库搜 `mqtt|opc|WebSocket|EventSource`，**只出现在注释和计划文档里**（`controller.ts:21`、`external.ts:80`、`scene-schema/src/index.ts:68`），无一行实现。

**阻断三：Studio 硬编码内存仓储**
`studioSession.ts:90` `readonly storage = createMemoryStorage();`
`storage-postgres` 有完整实现（6 个仓储 + `migrations/001_init.sql` 时间分区），但只被 `storage-testkit` 的契约测试跑到，
**没有任何运行时代码 import 它**（apps 侧 grep 为零）。刷新页面 = 一切归零。

### 2.3 但缝留得对（这是好消息）

- **唯一入口收敛**：`world.ts:288 ingestExternalFrame` → `step()` 内 `external.ts:80 resolveExternalMotion`（纯函数）。
- **帧源抽象已存在**：`replay-core/src/controller.ts:26 ExternalFrameSource { feedTo, rewind }`，`attachSource` 挂载（`:111`）。
  **新增一种协议 = 实现这个接口**，内核一行不用改。接 MQTT 的净工作量其实只有适配器本身 + 一个服务端。
- **模式切换已就绪**：`sim / external / hybrid` 三级（`:11 DataMode`），可按实体粒度决定"听仿真还是听现场"。
- **数据绑定字段已预留**：`scene-schema` 的 `DataBinding` 有 `sourceId`（"CSV 列组、MQTT 主题、MES 接口"）和 `externalKey`（"PLC tag"）——
  语义设计是对的，只是没有第二个 Adapter 来填。

## 3. 适配复杂工厂

### 3.1 评分

| 能力 | 判定 | 证据 |
| --- | --- | --- |
| 场景数据驱动 | ⚠️ 契约有，入口无 | `TwinScene` 是纯 JSON 可往返；但 `studioSession.ts:102` 直接 `buildCenterScene(CENTER_PARAMS)`，**没有"导入任意场景 JSON"的入口** |
| 模板参数化 | ❌ 只有 6 个旋钮 | `CenterTemplateParams` 仅 `maxWip / produceInterval / highWater / externalLanes / aisles / scale`；`scale` 只是整体乘系数 |
| 真实尺寸布局 | ❌ 坐标写死 | `template.ts` 函数体里 `aisleXs=[8,16]`、`RACK.bays=5`、`RACK_LEVELS`、`MAIN_EAST=19` 全是常量。**想表达"120m×60m、3 线 20 工位"必须改代码** |
| 规模 | ⚠️ 45 实体 | 实跑 `buildCenterScene()`：声明实体 **45** 个（transport 15 / transfer 4 / cassette 4 / asrs 4 / inspect 2 / pack 2 / labeler 2 / stacker 2 / truck 2 …）+ 运行期 spawn 的货物与托盘 |
| 渲染性能 | ⚠️ 货物有池，设备没有 | 货物走 `CargoPool` 单 `InstancedMesh`（容量 2048，`CargoPool.ts:34`）；**其余设备每个都 `new THREE.Group`**（`entityMeshes.ts`），无 LOD、无视锥剔除、无分块 |
| 仿真性能 | ⚠️ O(N) 全量 | `world.ts stepOnce` 每步全量遍历实体推 motion，各 behavior 再各遍历一遍；无空间索引、无分区 |
| 坐标系 | ❌ 单层米制 | `TwinTransform` 只有 `position/rotation/scale`，**无楼层/标高、无经纬度**；网格固定 64×64 |
| 多楼层 | ❌ | 无概念 |
| 插件开放度 | ⚠️ 逻辑开放，外观不开放 | 行为/指标/面板可经 `PluginHost` 接入不改内核；但**新设备 3D 外观要在 `entityMeshes.ts` 按 `kind` 加分支** → 仍需改 Studio；且插件是静态 import，无运行时发现 |
| 告警 / OEE | ❌ | `analytics-core` 只有事后统计（停机按 `downStatuses` 算时长），无阈值告警、无 OEE、无规则引擎 |

### 3.2 最大风险：布局真相在代码里，不在数据里

这是"能否适配复杂工厂"的**根问题**：

```
真实工厂（CAD / MES 台账 / 现场测绘）
        ↓  ✂️ 这一刀是断的：靠人读图 → 手写成 TS 常量
centerTemplate()  ← 布局真相在这里
        ↓  ✅
   TwinScene JSON
        ↓  ✅
     世界内核
```

只要布局真相还在 TS 函数体里，"一天内建一条线"就不可能成立——
因为改一根皮带的位置要改代码、跑测试、重新构建。
**这也是你一直在做的 Graph Reconstruction Engine（CAD → 可仿真拓扑图）要解决的那一刀**，
目前它与 twin-platform 之间**还没有接上**。

## 4. 缺口清单与优先级

| P | 缺口 | 影响 | 粗估 |
| --- | --- | --- | --- |
| **P0** | 服务端（哪怕一个薄 Node/Bun API） | 没有它，Postgres、实时接入、多用户全部无从谈起 | 3–5 人日 |
| **P0** | 场景 JSON 导入/导出入口 | 场景从"代码产物"变成"可交付数据"，也是接 CAD 的前置 | 2–3 人日 |
| **P0** | 布局数据化（把 `aisleXs`/`RACK`/坐标抽成场景数据或布局 DSL） | 决定"一天建线"能否成立 | 5–8 人日 |
| **P1** | 第二种数据源 Adapter（MQTT 或 WebSocket） | 验证 `ExternalFrameSource` 抽象真的够用；接 MES/PLC 的样板 | 3–5 人日 |
| **P1** | Studio 切到 `storage-postgres`（经服务端） | 刷新不丢、可协作、可回放历史 | 3–5 人日 |
| **P1** | 渲染规模化（设备实例化 / LOD / 剔除 / 分区） | 从 45 实体到千级设备的门票 | 5–10 人日 |
| **P2** | 多楼层 / 标高 / 厂区坐标 | 跨车间、跨楼层场景 | 3–5 人日 |
| **P2** | 阈值告警 + 规则引擎 + OEE | 从"事后看板"到"实时告警" | 5 人日 |
| **P2** | 设备外观插件化（随插件下发 mesh 描述） | 第三方加设备不必改 Studio | 3–5 人日 |
| **P2** | 运行时插件发现 / 远程插件（计划明确排除） | 生态化 | 8+ 人日 |

## 5. 建议路线

**第一段（~2 周）：把"演示"变成"可交付"**
服务端 + 场景 JSON 导入导出 + Studio 接 Postgres。做完之后：场景是数据、可存可取、刷新不丢。

**第二段（~2 周）：接通现场**
写一个 MQTT（或 WebSocket）Adapter 走完 `ExternalFrameSource` 全链路，
用一个真实点位表驱动几个实体。**这一段的价值不在协议本身，而在验证"外部真相 → 内核"这条缝够不够宽**。

**第三段（~3 周）：扛规模**
布局数据化（把 `centerTemplate` 的常量抽成布局数据）+ 渲染实例化/剔除 + 仿真分区。
这一段做完，才谈得上"适配复杂工厂现状"。

> 顺序建议：**先做第一段再做第二段**。现在没有服务端，接 MQTT 也只能在浏览器里跑 mock，
> 做完也证明不了什么。
